# Hookdock — приём и маршрутизация вебхуков

Самодостаточный сервис-«ловушка» для входящих вебхуков с визуальным конструктором маршрутизации
в духе Zapier/Albato. Каждый запрос сохраняется с методом, путём, заголовками, сырым телом и
разобранным JSON, после чего сценарии могут отфильтровать его по полям и переслать, залогировать
или трансформировать данные.

Запросы и сценарии живут в **комнатах**: у каждой комнаты свой slug в адресе вебхука, свой лог и
свои сценарии. Комнаты не видят данные друг друга.

## Возможности

- **Комнаты** со случайным slug и своим эндпоинтом: `/hook/{room}/{endpoint}`. Slug
  (`785e9e9c1b10-9a7be406d763`) и эндпоинт (`hook-7f3a9c`) генерируются при создании комнаты;
  эндпоинт можно изменить или перегенерировать в настройках комнаты. Боковая панель загружает
  **последние 20** комнат со счётчиками, остальные находятся поиском по названию или slug — при
  сотнях комнат список не тянет всю таблицу и не считает её на каждое открытие.
- Приём **любых** методов (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`) по адресам
  `/api/webhook/{room}/{endpoint}` и `/hook/{room}/{endpoint}`. Эндпоинт может нести собственный
  путь: `/hook/{room}/stripe/payment/succeeded` сохраняется как `stripe/payment/succeeded`.
- Приём **асинхронный**: запрос сохраняется, сценарии ставятся в очередь, ответ `202` отдаётся
  сразу (`queued: N`). Условия и действия выполняет отдельный сервис `worker`, поэтому медленный
  внешний API не задерживает отправителя.
- Сбои пересылки повторяются с backoff (сеть, таймаут, `408`, `429`, `5xx`); повтор не отправляет
  заново действия, которые уже выполнились. Каждый шаг пишется в журнал с кодом ответа и временем.
- Хранение заголовков, query-параметров, сырого тела и JSON в PostgreSQL (`jsonb`). Тела
  `multipart/form-data` сохраняются целиком.
- CORS-preflight на адресах приёма, чтобы ловушку можно было вызвать из браузера на другом Origin.
- Защита от SSRF в пересылке (loopback, link-local и метаданные облака запрещены) и лимиты на вход и
  приём; демо-вход выключен флагом `DEMO_LOGIN`.
- **Подпись вебхуков** (необязательно, на комнату): при включённом секрете приёмник требует
  `X-Hookdock-Signature: sha256=<HMAC-SHA256 сырого тела>`; запрос без верной подписи получает `401`
  и не попадает в лог. Секрет показывается один раз, а API отдаёт только признак `has_secret`.
  Комната может дополнительно требовать `X-Hookdock-Timestamp`: подпись тогда считается по
  `«<timestamp>.<тело>»`, а старое время отклоняется — иначе перехваченный запрос можно повторять вечно.
- **Дедупликация доставок** (необязательно, на комнату): один заголовок (`X-GitHub-Delivery`,
  `Stripe-Event-Id`, …) объявляется идентификатором доставки. Повтор сохраняется в журнал с
  `duplicate_of`, но не запускает сценарии и всё равно получает `202` — иначе отправитель повторял бы
  доставку, которую ему велели прекратить.
- **Список разрешённых адресов** (необязательно, на комнату): диапазоны CIDR, с которых комната
  принимает доставки. Сравнение идёт по упакованным байтам, поэтому `::1`, `::ffff:7f00:1` и
  `::ffff:127.0.0.1` — один и тот же отправитель. Запрос с чужого адреса получает `403` **до**
  сохранения: он не попадает ни в лог, ни в очередь. Пустой список — принимаем со всех (так ведут себя
  все комнаты, созданные до появления настройки).
- Автообновляемый лог запросов: фильтры по методу/эндпоинту/тексту и периоду (час, сутки, неделя,
  месяц или свой диапазон), пагинация, детальная карточка с подсветкой JSON и копированием запроса
  как cURL, экспорт текущей выборки в JSON, NDJSON или CSV. Фильтр по эндпоинту показывает 15 самых
  частых, остальные ищутся по подстроке — комната может принимать на сотни путей.
- **Повтор маршрутизации**: сохранённый запрос можно провести по включённым сценариям комнаты заново,
  а упавший запуск — повторить отдельным свежим запуском. Исходный запуск остаётся в журнале со
  своими шагами и попытками.
- Обновления в реальном времени по WebSocket (без опроса по таймеру): новые запросы, результаты
  маршрутизации и изменения сценариев приходят из бэкенда через Postgres `LISTEN/NOTIFY`.
- Конструктор сценариев: триггер → условия → действия, включение/пауза, история запусков
  (`в очереди` / `выполняется` / `success` / `failed` / `skipped`) с таймлайном шагов: тип действия,
  код ответа, тело ответа и длительность каждой попытки. Сценарий принадлежит одной комнате и
  срабатывает только на её запросы.
- Действия: пересылка HTTP-запроса, запись в лог, трансформация полей; шаблоны `{{ path }}`.
- **Алерты о падениях**: терминальные сбои считаются, после `WORKFLOW_FAILURE_THRESHOLD` подряд
  сценарий выключается автоматически с причиной в интерфейсе, а необязательный
  `ALERT_WEBHOOK_URL` получает JSON (Slack/Discord-совместимый `text`).
- **Предохранитель пересылки**: сбой запоминается по адресу, а не по сценарию. После нескольких
  терминальных ошибок подряд адрес пропускается на кулдаун (запуск откладывается, попытка не
  сжигается), затем пропускается одна проба; страница «Доставка» показывает такие адреса и умеет
  сбросить один вручную.
- **Перенос правил**: экспорт комнаты файлом и импорт в другую установку (секреты подписи не
  выгружаются — API сообщает, сколько подписей файл не нёс) и защита от одновременной правки
  списка действий (`409` вместо молчаливой перезаписи чужой вкладки).
- **Роли и доступы**: `admin`, `editor`, `viewer`. Роль живёт на пользователе, а не в токене,
  поэтому понижение действует со следующего запроса, а не через 12 часов. Роль и `scope` токена —
  два независимых ограничения, и проверяются оба: `viewer` и токен `scope: read` получают `403`
  на любой изменяющий метод, а управление аккаунтами доступно только `admin`.
- **Журнал аудита**: кто, что и когда изменил — с дифом `{поле: [было, стало]}`, фильтрами по
  комнате, действию, автору и тексту. Записи денормализованы (копии email, slug и названия),
  поэтому остаются читаемыми после переименования аккаунта или удаления комнаты; секреты подписи
  вырезаются до построения дифа и в журнал не попадают никогда.
- **История версий сценария**: каждое сохранение кладёт полную конфигурацию правила в историю, а
  откат — это новое сохранение, а не перезапись: текущее состояние тоже попадает в историю, так что
  откат можно отменить тем же списком. Снимки хранят секреты подписи (иначе восстановленная
  пересылка ушла бы без подписи), но наружу отдаются отредактированными — `signed: true`.
- **Массовые операции в логе**: чекбоксы в таблице и в карточках, «выбрать все на странице»,
  массовый повтор маршрутизации и массовое удаление. Запрос с ещё выполняющимся запуском не
  удаляется и не повторяется — он пропускается с причиной, потому что это отменило бы
  маршрутизацию, которая идёт прямо сейчас. Запрос с явным списком `ids`, а не с текущим фильтром:
  одно неверное нажатие не должно удалять результат поиска, которого никто не считал.
- **Повтор с правкой**: «Отправить с правками» создаёт **копию** запроса с исправленной полезной
  нагрузкой и маршрутизирует её. Исходная строка остаётся ровно такой, какой её отправил отправитель:
  журнал — это доказательство, а журнал шагов запуска не должен описывать тело, которое никогда не
  приходило. Копия помечена `replayed_from`, а не `duplicate_of` (последнее значит «отправитель
  повторил доставку, и мы её намеренно не маршрутизировали»).
- **Сохранённые фильтры**: набор фильтров запоминается для каждой комнаты, поэтому «что прислал
  Stripe сегодня» не нужно собирать заново на каждом открытии. Хранится в браузере
  (`localStorage`), а не на сервере: это предпочтение этого рабочего места, а не свойство установки.
- **Аналитика комнаты**: объём по часам, доля успешных запусков, p50/p95/максимум по каждому типу
  действия и топ эндпоинтов за окно (час, 6 часов, сутки, 3 дня, неделя). Задержки берутся из
  журнала шагов — это единственное место, где видно, что цель отвечает 4 секунды, хотя запуск
  формально `success`; рост p95 заметен раньше, чем начинаются падения. Доля успеха считается по
  завершённым запускам: очередь не должна выглядеть как ошибка. Тихие часы остаются на графике
  нулями, а не пропусками.
- **Метрики для мониторинга**: `GET /api/metrics` отдаёт установку в формате Prometheus
  (`text/plain`): очередь, запуски по статусам, живость воркера, открытые предохранители и порог их
  срабатывания. Публичный, как `/api/health`, — у скрейпера нет токена, — и содержит только числа:
  ни полезной нагрузки, ни комнат, ни адресов пересылки.
- **Поиск по заголовкам**: строка поиска в логе ищет и по блоку заголовков, поэтому «что присылал
  GitHub с `X-GitHub-Event: push`» отвечается одним запросом, а не открытием строк подряд. Индекс —
  GIN trigram по текстовой форме `headers`, то есть по тому же выражению, что и сравнение.
- **Мобильный лог**: на узких экранах запросы показываются карточками (метод, путь, время,
  маршрутизация), а не таблицей из семи колонок; фильтры и экспорт перестраиваются в две колонки.
- Русский интерфейс, светлая тема по умолчанию и тёмная по переключателю.

## Стек

- **Frontend:** Vue 3 (`<script setup>`), Vite, Pinia, Vue Router, Tailwind CSS v4
- **Backend:** нативный PHP 8.3 без фреймворка и Composer, PDO/pgsql, JWT
- **База:** PostgreSQL 16
- **Окружение:** Docker Compose — nginx (статика + прокси), php-fpm (`api`), воркер
  маршрутизации (`worker`), демон реального времени (`ws`), Postgres

## Быстрый старт

```bash
docker compose up --build
```

Откройте <http://localhost:8080> и войдите:

| Email | Пароль |
| --- | --- |
| `admin@hookdock.local` | `123456` |

Демо-вход — это отдельный флаг: кнопка **«Войти в демо-кабинет»** и подсказка с паролем
появляются, только пока `DEMO_LOGIN=1` (значение по умолчанию). Сами креды приходят с сервера
(`GET /api/auth/config`), в бандл фронтенда они не попадают. На публичной установке поставьте
`DEMO_LOGIN=0` и задайте свой `JWT_SECRET` — страница входа предупредит, если секрет остался
дефолтным.

Схема БД, миграции и администратор создаются автоматически при первом запуске
(`backend/migrate.php` вызывается из entrypoint контейнера `api`). Ручной SQL не нужен.

Параметры можно переопределить, скопировав `.env.example` в `.env` (`APP_PORT`, `DB_PASSWORD`,
`JWT_SECRET` и т.д.). Значения по умолчанию работают сразу.

## Комнаты

Комната — это отдельное хранилище входящих запросов и сценариев со своим адресом. При первом
запуске миграция создаёт комнату **«Общая»** со slug `default`, поэтому прежние адреса продолжают
работать. Её можно переименовать или удалить, как любую другую.

- Slug комнаты уникален без учёта регистра и состоит из `[a-z0-9-]`, начинается с буквы или цифры,
  до 64 символов. Он случаен и не связан с названием: две группы по 12 hex-символов через дефис
  (`785e9e9c1b10-9a7be406d763`). Форма генерирует его и показывает будущий адрес, а если клиент не
  прислал slug — сервер подставляет случайный. Поэтому переименование комнаты не меняет её адрес.
- Повтор slug исключён: сервер проверяет значение перед созданием (и перед сменой) и при совпадении
  отвечает 422 «Slug комнаты уже занят, сгенерируйте новый» — сам он другое значение не подбирает.
  Уникальный индекс `lower(slug)` закрывает гонку параллельных запросов.
- Slug можно сменить только явно через API (`PUT /api/rooms/{id}` с полем `slug`; пустое значение
  просит новый случайный): переименование комнаты его не трогает, поэтому не ломает настроенные
  интеграции. При смене slug старый адрес отвечает 404. Уже созданные комнаты (включая `default`)
  сохраняют свои slug.
- Вебхук в несуществующую комнату **не создаёт** её и не сваливается в `default` — приёмник
  отвечает 404.
- Удаление комнаты каскадно удаляет её запросы, запуски и сценарии.

Адрес `/hook/{x}` неоднозначен: это может быть комната без эндпоинта или эндпоинт комнаты
`default`. Приёмник сначала ищет комнату с таким slug; если её нет, сегмент считается эндпоинтом
комнаты `default`. Поэтому одиночный `/hook/stripe` по-прежнему попадает в «Общую», а
`/hook/payments/retry` — в комнату `payments`, если она существует.

## Тестовый вебхук

```bash
curl -X POST http://localhost:8080/api/webhook/default/stripe \
  -H "Content-Type: application/json" \
  -d '{"event":{"type":"payment.succeeded"},"customer":{"email":"ada@example.com"}}'
```

В PowerShell используйте `curl.exe` (обычный `curl` — алиас `Invoke-WebRequest`) либо готовый
скрипт:

```powershell
scripts/smoke.ps1 -BaseUrl http://localhost:8080
```

Адреса приёма (публичные, без авторизации):

- `/api/webhook/{room}/{endpoint}` — основной адрес из интерфейса;
- `/api/webhook/{room}` — комната без эндпоинта (эндпоинт сохраняется как `default`);
- `/hook/{room}/{endpoint}`, `/hook/{room}` — короткие алиасы;
- `/api/webhook/{endpoint}` и `/hook/{endpoint}` — эндпоинт комнаты `default` (совместимость).

Эндпоинт может нести собственный путь любой глубины: `/hook/{room}/stripe/payment/succeeded`
сохранится с эндпоинтом `stripe/payment/succeeded`, а комната по-прежнему определяется первым
сегментом. Неизвестная комната в таком адресе — 404.

Slug эндпоинта сохраняется вместе с запросом — по нему удобно строить сценарии для конкретного
источника.

У каждой комнаты есть собственный эндпоинт (`rooms.endpoint`): он генерируется автоматически
(`hook-` + 6 hex-символов), показывается в адресе «Слушает на» и в триггере сценариев с `*`, и
меняется в настройках комнаты. Приём от этого не ограничивается: любой путь под комнатой
по-прежнему сохраняется, поэтому старые адреса продолжают работать.

## Сценарии

Сценарий состоит из **триггера → условий → действий**:

1. **Триггер** — либо slug эндпоинта внутри комнаты (`*` — все эндпоинты комнаты),
   либо cron-расписание (см. «Запуск по расписанию» ниже).
2. **Условия** — дерево групп `И` / `ИЛИ`, вложенность до 5 уровней (до 40 условий).
   Хранится как `{"mode": "all"|"any", "rules": [...]}`, где правило — либо условие,
   либо такая же группа, поэтому «type = payment И (name = Ada ИЛИ name = Bob)»
   выражается напрямую. Плоский список от старого клиента читается как группа `all`.
   Пути читаются из контекста запроса:
   `body.customer.email`, `query.source`, `headers.x-github-event`, `meta.method`, `transformed.*`.
   Операторы: `equals`, `not_equals`, `contains`, `not_contains`, `exists`, `not_exists`,
   `gt`, `gte`, `lt`, `lte`, `regex`.
3. **Действия** — выполняются по порядку:
   - `forward` — HTTP-запрос на внешний URL (POST/PUT/PATCH/GET/DELETE), тело: исходное,
     трансформированное, сырое или свой JSON-шаблон; свои заголовки; необязательная
     HMAC-подпись исходящего (`secret` → заголовок `X-Hookdock-Signature`);
   - `transform` — сопоставление ключей результата с путями контекста
     (`{"email": "body.customer.email"}`);
   - `delay` — пауза на N секунд, затем остальные действия; попытки не расходует и при
     повторе не ждёт второй раз;
   - `log` — запись сообщения с подстановкой `{{ body.field }}`.

Порядок и остановка: `priority` (0–1000, больше — раньше) задаёт порядок запуска
сценариев одного запроса, а `stop_processing` превращает набор правил в «срабатывает
первое подходящее» — остальные `pending`-запуски этого запроса получают `skipped` с
пометкой, какой сценарий их остановил. Если правило упадёт, остальные всё равно выполнятся.
Кнопка «Дублировать» создаёт копию сценария выключенной, чтобы правка варианта не удвоила
пересылки.

Проверка правил (dry run) — `POST /api/requests/{id}/preview`: условия считаются на
сохранённом теле, каждое действие описывается (URL, метод, заголовки, тело, подпись), но
ничего не ставится в очередь и не отправляется. Без тела запроса проверяются все активные
сценарии комнаты; с `{conditions, actions}` — черновик из редактора. Адрес `forward`
по-прежнему проходит `UrlGuard`, чтобы предпросмотр не одобрял цель, которую воркер отклонит.

Каждый сценарий, подошедший по эндпоинту, создаёт запуск: сначала `pending`, затем `running` и в
итоге `success`, `failed` или `skipped`. Запуск виден в карточке запроса вместе с шагами каждой
попытки. Ошибки действий не влияют на уже отданный ответ `202`: отправитель получил его до того,
как сценарий начал выполняться.

Временные сбои `forward` повторяются (`ROUTING_MAX_ATTEMPTS`, по умолчанию 3 попытки) с задержкой
`ROUTING_RETRY_BASE` → 1, 2, 4 секунды: сеть, таймаут, `408`, `429`, `5xx`. Ответы `4xx` и пустой
URL не повторяются — это ошибка настройки, а не сбой сети. Повтор пропускает действия, уже
записанные как `success`, поэтому получатель не увидит одну и ту же пересылку дважды.
Исключение — `transform`: оно не имеет побочных эффектов и пересчитывается на каждой попытке, иначе
`forward` с `payload: "transformed"` отправил бы пустое тело.
Сценарий всегда принадлежит комнате: `room_id` или `room` (slug) обязателен при создании, а
перенести сценарий в другую комнату нельзя (ответ 422) — иначе он бы молча начал срабатывать на
чужие вебхуки.

Пример через API:

```bash
TOKEN=$(curl -s -X POST http://localhost:8080/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@hookdock.local","password":"123456"}' | jq -r .token)

curl -X POST http://localhost:8080/api/workflows \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{
    "room": "default",
    "name": "Уведомить CRM",
    "endpoint": "stripe",
    "enabled": true,
    "conditions": [{"path": "body.event.type", "operator": "equals", "value": "payment.succeeded"}],
    "actions": [{"type": "forward", "url": "https://example.com/hooks/crm", "method": "POST", "payload": "body"}]
  }'
```

### Запуск по расписанию

Сценарий может срабатывать не на вебхук, а по cron-расписанию. Переключатель один —
поле `schedule_cron`: есть выражение — правило запускается планировщиком, пустая строка
или `null` — правило снова слушает вебхуки. Отдельного флага «включено расписание» нет,
поэтому два состояния не могут разойтись.

- Пять полей: минуты, часы, день месяца, месяц, день недели. Поддерживаются `*`, `n`,
  `a-b`, `*/n`, `a-b/n` и списки через запятую. Имён месяцев и дней, `@daily`, `?`, `L`,
  `W`, `#` нет: выражение, смысл которого зависит от реализации, лучше отклонить, чем
  сохранить. `7` = воскресенье. Если ограничены и день месяца, и день недели, достаточно
  совпадения любого из них (как в классическом cron).
- Время — **UTC**, чтобы расписание не переезжало вместе с часовым поясом хоста.
  `0 9 * * 1-5` — 12:00 по Москве.
- Выражение, которое не сработает никогда (`0 0 31 2 *`), отклоняется с `422`: иначе
  правило навсегда осталось бы в очереди планировщика.
- Запуск по расписанию приходит **без запроса**: `workflow_runs.request_id` = `null`,
  тело, заголовки и параметры пусты, а в шаблоне доступны `meta.workflow` и
  `meta.schedule`. Условия такому запуску не с кем сравнивать — они не проверяются,
  и редактор их скрывает.
- Пропущенные слоты (воркер лежал) догоняются **один раз**: следующий слот считается от
  текущего момента, а не от пропущенного. Пятиминутная остановка не превращается в
  лавину одинаковых запусков.
- `schedule_next_at` пересчитывается при сохранении, при включении правила и при откате
  версии. Ручной запуск его не трогает.

`POST /api/workflows/{id}/run` — «Запустить сейчас»: ставит один запуск немедленно, с тем
же пустым контекстом, что и расписание. Это единственный способ проверить правило с
расписанием, не дожидаясь слота, и он работает даже для выключенного сценария — оператор
как раз спрашивает «оно вообще работает?».

```bash
curl -X POST http://localhost:8080/api/workflows/7/run \
  -H "Authorization: Bearer $TOKEN"
# 202 {"data":{"id":42,"workflow_id":7,"request_id":null,"queued":1}}
```

В журнале запусков такой запуск помечен «расписание» или «вручную», кнопка «Запрос»
у него отсутствует, а в колонке запроса стоит «без запроса». Повторить его тоже можно:
повтор создаёт новый запуск без запроса.

### Алерты о падениях и авто-выключение

Приёмник отвечает `202` до выполнения сценариев, поэтому сломанный адрес пересылки никого не
беспокоит: отправитель доволен, а ошибка лежит в журнале, который никто не открывает. Поэтому
каждый **терминальный** сбой запуска (после всех повторов) считается:

- `WORKFLOW_FAILURE_THRESHOLD` (по умолчанию 3) — сколько сбоев подряд выключает сценарий.
  Успешный запуск и ручное включение обнуляют счётчик, `skipped` его не меняет.
- Выключенный автоматически сценарий помечается в интерфейсе баннером и бейджем «выключен»,
  с причиной и последней ошибкой; обычная пауза выглядит иначе. API отдаёт
  `consecutive_failures`, `disabled_reason`, `disabled_at` и вычисляемый `auto_paused`,
  `/api/stats` — `workflows_auto_paused`.
- `ALERT_WEBHOOK_URL` — необязательный адрес, куда уходит JSON с полями `text` (подходит для
  входящего вебхука Slack/Discord «как есть»), `event` (`workflow.failed` / `workflow.paused`),
  `workflow`, `room`, `run`, `request`. Пустое значение отключает отправку, счётчики и
  авто-выключение продолжают работать.
- `ALERT_COOLDOWN_SECONDS` (по умолчанию 900) — не чаще одного сообщения об ошибках сценария за
  интервал, иначе упавший на час адрес присылал бы сообщение на каждый вебхук. Уведомление о
  выключении отправляется всегда: оно одно на серию.

Уведомление — побочный канал: недоступный адрес алерта пишется в `docker compose logs -f worker` и
не меняет исход запуска. Адрес проверяется тем же `UrlGuard`, что и `forward`, поэтому опечатка в
`ALERT_WEBHOOK_URL` не отправит запрос в облачные метаданные.

### Предохранитель пересылки

Авто-выключение сценария — это реакция на серию сбоев, но она бьёт не по той цели: один мёртвый
адрес выключает правило, которое оживёт вместе с ним. Поэтому сбой запоминается **по адресу**
(`scheme://host:port`), а не по сценарию:

- После `FORWARD_BREAKER_THRESHOLD` (по умолчанию 2) терминальных сбоев подряд адрес перестаёт
  вызываться. Засчитывается только окончательный вердикт запуска: пока у него остались повторы,
  адрес не считается сломанным, иначе пять секунд сетевой икоты открывали бы предохранитель.
- Отказ адреса записывается шагом `skipped`, а запуск **переоткладывается** на момент следующей
  проверки, не сжигая попытку: цель не вызывалась, и превращать это в `failed` было бы нечестно.
  Строка `pending` не должна жить вечно (отсрочка не тратит `attempts`), поэтому после
  `FORWARD_BREAKER_DEFERRALS` (3) кулдаунов запуск завершается `skipped` с тем же объяснением.
- `FORWARD_BREAKER_COOLDOWN` (60 с) — через сколько разрешается **одна** пробная доставка.
  Состояние выводится из `next_probe_at`, поэтому фоновый процесс для «выздоровления» не нужен:
  первая доставка после кулдауна и есть проба, и её исход либо закрывает адрес, либо снова
  открывает.
- `GET /api/breakers` показывает адреса и `retry_in`; `POST /api/breakers/reset` удаляет строку —
  это ответ оператора «я починил». Строка именно удаляется: оставленный счётчик сбоев открыл бы
  предохранитель на первой же ошибке, и сброс выглядел бы бесполезным.
- Dry run описывает предохранитель (`breaker`, `breaker_retry_in`), но не забирает единственную
  пробу — иначе предпросмотр отодвигал бы настоящую проверку на целый кулдаун.

Состояние общее для установки: адрес не принадлежит комнате, и две комнаты, шлющие в один CRM,
должны видеть один вердикт.

### Перенос правил между установками

`GET /api/rooms/{id}/workflows/export` отдаёт файл `hookdock.room` (`version: 1`) — условия,
действия, приоритеты и флаги комнаты. `POST /api/rooms/{id}/workflows/import` принимает его
обратно:

- **Секреты не выгружаются.** HMAC нельзя проверить по хешу, поэтому секрет хранится как есть и
  никогда не покидает API; подписанная пересылка приходит как `signed: true`, а импорт считает
  такие действия в `secrets_not_imported`. Иначе правило выглядело бы перенесённым, а получатель
  молча отклонял бы каждый запрос.
- `room_id` берётся из URL, а не из документа: экспорт из стенда не должен уметь записать в
  продакшен, назвав его в файле.
- Импорт только добавляет: совпавшее имя получает числовой суффикс, ничего не перезаписывается и
  не удаляется, а вся пачка валидируется целиком — половина набора хуже отказа, потому что
  непонятно, какой половины нет.
- **Одновременная правка.** `PUT /api/workflows/{id}` принимает `actions_version`, которую редактор
  загрузил. Если она не совпадает с сохранённой, ответ — `409` с актуальной версией в
  `error.actions_version`: иначе вторая вкладка молча заменила бы список действий, включая только
  что добавленную пересылку. Версия растёт только при реальном изменении действий, поэтому
  переименование сценария не делает чужой черновик устаревшим; клиент без версии (curl, старый
  скрипт) продолжает работать.

### Роли, аудит и история версий

Три вопроса, на которые продукт раньше не отвечал: кто что может, кто это сделал и как правило
выглядело до того, как сломалось.

- **Роль и токен — разные вещи.** `users.role` (`admin`, `editor`, `viewer`) ограничивает
  человека, `scope` токена (`api`, `read`) ограничивает сам токен. Проверяются оба:
  `editor` с read-токеном читает, но не пишет, а `viewer` с полным токеном всё равно получает
  `403` на любой изменяющий метод. Роль хранится на пользователе, а не в JWT, поэтому понижение
  действует со следующего запроса — ждать истечения 12-часового токена не нужно.
- **Кто чем управляет.** `admin` может всё, включая `/api/users` и роли; `editor` — продукт
  (комнаты, правила, повтор, предохранитель); `viewer` — чтение, экспорт, dry-run и журнал
  запусков. `admin` нужен отдельно (`Auth::requireAdmin`): редактор, который мог бы выдать себе
  `admin`, сделал бы роли декоративными.
- **Установку нельзя оставить без администратора.** Снять роль `admin` с себя, удалить себя и
  убрать последнего администратора — `422`. Иначе единственная страница, где роль можно вернуть,
  стала бы недоступна тому, кто мог её вернуть.
- **Пароль — только по длине** (8–72 байта). Правила вида «одна цифра и один символ» толкают
  людей к `Password1!`, а bcrypt молча обрезает пароль на 72 байтах — верхняя граница не
  косметическая. Смена своего пароля требует текущий, иначе украденный токен — это захват
  аккаунта навсегда. Смена чужого пароля доступна `admin`, и в журнал попадает только факт
  изменения, никогда не хеш и не значение.
- **Журнал аудита** (`GET /api/audit`) — append-only и денормализованный: `actor_email`,
  `actor_role`, `room_slug` и `object_label` — копии, а FK идут `ON DELETE SET NULL`, поэтому
  запись остаётся понятной после переименования аккаунта и удаления комнаты. Диф —
  `{поле: [было, стало]}`; небольшое вложенное значение (дерево условий) пишется целиком, иначе
  запись «условия изменились, 1 правило» выглядела бы правдой и ничего не объясняла; крупное
  сжимается до счётчика, а диф длиннее 4 КБ заменяется маркером размера. Обе стороны дифа
  редактируются **до** его построения, поэтому секрет подписи не может попасть в таблицу вовсе.
- **История версий** (`GET /api/workflows/{id}/versions`) — снимок `conditions` + `actions` на
  каждое сохранение (создание, правка, переключение, импорт, откат); список отдаёт 100 последних
  версий. Существующим правилам миграция `013` кладёт `baseline`, чтобы история начиналась не с
  пустоты.
  Откат — **новая** версия с `change: 'rollback'`: удалять промежуточные значило бы потерять ответ
  на «кто и когда это вернул». `actions_version` при откате ведёт себя как при обычном сохранении
  и растёт только при реальном изменении списка действий.

### Долгоживущие токены

Сессия в браузере живёт 12 часов и умирает вместе с `JWT_SECRET`; ночному экспорту или CI нужен
ключ, который переживёт и то и другое — и который можно **отозвать**.

- `POST /api/tokens` выпускает ключ `hd_<12 hex><48 hex>`. В базе лежит только SHA-256, поэтому
  дамп Базы — не набор паролей; `prefix` (первые 18 символов) — не секрет, а ключ поиска: запрос
  находит свою строку одним индексным поиском, не пересчитывая хеши всех токенов. Открытый текст
  отдаётся **один раз**, в `201`, как секрет подписи комнаты.
- `scope` берётся из строки, роль — из `users`. Read-ключ остаётся read-ключом, даже если его выдал
  администратор, а `viewer` с полным ключом всё равно получает `403` на запись: ограничение
  креденшела и ограничение человека не складываются в одно.
- `expires_at` — абсолютный момент; `null` значит «не истекает», что нормально для интеграции,
  которую никто не собирается перевыпускать. Голая дата (`2027-06-01`) означает **конец** этого дня,
  а не его начало. Прошедшая дата — `422`, а не мёртвый ключ, который выглядит рабочим.
- `DELETE /api/tokens/{id}` ставит `revoked_at`, но **не удаляет строку**: `last_used_at` — ответ на
  «успели ли воспользоваться утёкшим ключом». Отзыв действует со следующего запроса, повторный —
  `200` с `already: true`.
- `last_used_at` пишется не чаще раза в минуту: колонка отвечает «ключом пользовались с последнего
  просмотра», а не «в 12:00:03», и лишняя запись на каждый API-вызов удваивала бы стоимость пути.
- Выпуск, список и отзыв — только `admin`, как `/api/users`: токен действует как его аккаунт, так
  что выпустить его — это выдача прав, а не личная настройка. Страница «Токены» в интерфейсе
  видна только администратору.

### Список разрешённых адресов

Подпись доказывает, **что** отправило payload; список адресов говорит, **откуда** он может прийти —
это то, что реально есть у интеграции за фиксированным NAT.

- Хранится как `TEXT[]` в `rooms.ip_allowlist`, канонизируется: `10.0.0.1/8` → `10.0.0.0/8`, а
  голый адрес → `/32` или `/128`, чтобы показанное совпадало с тем, что сравнивается. Дубликаты
  схлопываются, максимум 64 записи.
- Проверка идёт **после** подписи и **до** `INSERT`, поэтому отклонённая доставка не попадает в лог
  и не ставится в очередь. Порядо́к именно такой: подделанный запрос должен получить ответ про
  подпись, а не подтверждение, что его адрес почти в списке.
- Сравнение — по упакованным байтам (`inet_pton` + маска), не по строкам: `::1`,
  `0:0:0:0:0:0:0:1`, `::ffff:7f00:1` и `::ffff:127.0.0.1` — один адрес в разных записях, и текстовая
  проверка пропустила бы все, кроме первой. IPv4-mapped разворачивается в обе стороны.
- Пустой список = принимать всех; непустой нераспознанный = запрет. `PUT /api/rooms/{id}` без
  ключа `ip_allowlist` сохраняет текущий список, явный `[]` выключает проверку — иначе
  переименование комнаты в форме, которая не показывает поле, молча открыло бы её всем.

### Контракт: OpenAPI и Postman

`docs/openapi.yaml` — единственный источник контракта: 44 пути, 55 операций, 25 схем запросов и
ответов, коды ошибок и примеры. Он проверяется `openapi-spec-validator`, поэтому дрейф между
описанием и реализацией видно сразу, а не после интеграции.

Рядом лежит запускаемая коллекция `postman/collections/Hookdock API/` (формат v3, файлы в Git, а
не один экспорт): 53 запроса в девяти папках — `Auth`, `Access`, `Rooms`, `Workflows`, `Delivery`,
`Ingest`, `Requests`, `Runs`, `Cleanup`. Каждый запрос несёт свои проверки, а `Auth / Login`
складывает токен в переменную `token`, из которой берут авторизацию остальные — поэтому коллекция
запускается одной командой без ручной подготовки:

```powershell
postman collection run "postman/collections/Hookdock API"
```

Порядок важен: папки выполняются по `order`, а не по алфавиту, потому что `Ingest` создаёт запрос,
который читают `Requests`, а `Rooms` — комнату, в которую он приходит (`Auth` 1000 → `Access` 1500 →
`Rooms` 2000 → `Workflows` 3000 → `Ingest` 4000 → `Requests` 5000 → `Runs` 6000 → `Delivery` 7000 →
`Cleanup` 9000). `Access` идёт сразу после входа, потому что проверяет роли на живом токене;
`Cleanup` удаляет созданный ею аккаунт.
`Workflows / Export room rules` складывает документ в переменную, а `Import room rules` берёт
именно его — так проверяется согласованность двух половин, а не заранее написанная фикстура.
`Runs / Retry run` пропускается, если журнал не нашёл ни одного запуска
(`pm.execution.skipRequest`), вместо отправки `{{run_id}}` в URL и бессмысленного 404; `Delivery /
Reset breaker` в такой же ситуации проверяет честный no-op (`reset: false`), потому что строка
предохранителя появляется только после реального сбоя пересылки.

## Как проходит вебхук

```
webhook ──► api (PHP-FPM)
              ├─ INSERT incoming_requests
              ├─ INSERT workflow_runs (pending) ──► 202 {queued:N}
              └─ NOTIFY request.created
                        │
                     Postgres  ◄── FOR UPDATE SKIP LOCKED ── worker
                        │                                     ├─ условия
                        │                                     ├─ действия (log/transform/forward)
                        │                                     └─ workflow_run_steps + attempt
                        └──NOTIFY request.updated──► ws ──► браузер
```

- `api` только принимает и сохраняет: тело, заголовки, query и `pending`-запуски. Ответ `202`
  отдаётся до того, как выполнится хоть одно действие.
- `worker` — отдельный контейнер (`php /var/www/backend/bin/worker.php`): забирает созревшие
  запуски, проверяет условия, выполняет действия, пишет шаг в `workflow_run_steps` и повторяет
  запуск при временном сбое (сеть, таймаут, `408`, `429`, `5xx`) с задержкой 1→2→4 с. Действия,
  уже записанные как `success`, при повторе пропускаются — пересылка не уйдёт дважды.
- `recoverStale()` возвращает в очередь запуски, чей воркер умер (контейнер перезапущен), по
  `locked_at` старше `ROUTING_STALE_MINUTES` (5 минут).
- `worker_heartbeats` — по строке на воркер, обновляется на каждой итерации цикла. Без него
  мёртвый воркер неотличим от простаивающей установки: очередь просто не движется, а журнал
  выглядит как комната без правил. `/api/health` и healthcheck контейнера `api`
  (`php backend/bin/healthcheck.php`, HTTP в этом контейнере не слушается) отвечают `503`, если
  старейший `pending`-запуск старше `HEALTH_QUEUE_MAX_AGE` (300 с) или если работа есть, а
  воркер не бился дольше `WORKER_STALE_SECONDS` (60 с). Пустая очередь без воркера —
  не ошибка: свежий том поднимается раньше первого цикла.

## Безопасность и эксплуатация

Приём вебхуков публичен по определению, поэтому границы заданы отдельно от авторизации.

- **Подпись вебхуков.** Комната может требовать `X-Hookdock-Signature: sha256=<hex>` — HMAC-SHA256
  от сырого тела. Сравнение идёт через `hash_equals`: побайтовое `===` выдаёт длину совпавшего
  префикса по времени ответа, чего достаточно, чтобы подобрать подпись по байту. Проверка стоит
  **до** `INSERT`, поэтому подделка не попадает в лог и не запускает сценарии; комната без секрета
  остаётся публичной. HMAC невозможно проверить по хешу, поэтому секрет хранится в БД как есть —
  но API никогда его не возвращает, только `has_secret`; значение показывается один раз при выдаче
  и меняется перевыпуском. Подпись включается и при создании комнаты: `POST /api/rooms` с
  `require_signature: true` выдаёт секрет тем же `INSERT`, поэтому комната не появляется в списке
  без подписи ни на секунду, а `201` — единственный ответ создания, который содержит `secret`.
- **Подпись со временем.** Подпись только по телу не отличает повтор от новой доставки: тот, кто
  перехватил один запрос, может отправить его снова, и сценарии комнаты выполнятся дважды. Флаг
  `require_timestamp` добавляет обязательный `X-Hookdock-Timestamp` (unix-время), подпись считается
  по `"<timestamp>.<тело>"`, а время вне `SIGNATURE_TOLERANCE_SECONDS` (300 с) отклоняется с `401`.
  Если заголовок времени пришёл, используется **только** форма с timestamp: откат на подпись по телу
  сделал бы заголовок декоративным. Флаг без секрета ничего не проверяет, поэтому такая комната
  остаётся публичной, а не отклоняет всё подряд.
- **Дедупликация доставок.** `rooms.dedup_header` называет заголовок, значение которого считается
  идентификатором доставки. Уникальный частичный индекс `(room_id, dedup_key)` — это и есть проверка:
  предварительный `SELECT` пропустил бы две одновременные доставки одного события, и обе считались бы
  первыми. Коллизия ловится по `23505`; повтор сохраняется с `duplicate_of`, но **не** ставится в
  очередь, а ответ остаётся `202` (с `duplicate: true`, `queued: 0`) — `409` заставил бы отправителя
  повторять доставку, которую ему велели прекратить. Дедупликация выключена по умолчанию: включение
  не должно молча терять повторы интеграций, которые законно шлют одно тело дважды. Настроенный
  заголовок, которого в запросе нет, — не ошибка: доставка обрабатывается как обычная.
- **Тикет WebSocket — не токен API.** 60-секундный тикет живёт в query string, поэтому
  `Auth::user()` принимает только токены со `scope: api`/`scope: read` (или без scope, для
  совместимости). Тикет со `scope: ws` даёт 401 на любом REST-маршруте.
- **Токены только для чтения.** `POST /api/auth/read-token` (нужен полный `api`-токен) выдаёт
  JWT со `scope: read` для дашбордов и коллег, которым нужен журнал, а не `DELETE /api/rooms/{id}`.
  Каждый изменяющий обработчик вызывает `Auth::requireUser($request, true)` и отвечает `403`
  («Токен только для чтения…»); чтение, экспорт и dry-run разрешены. Read-токен не может выдать
  себе подобный. `GET /api/auth/me` возвращает `scope`, чтобы SPA мог скрыть изменяющие кнопки.
  JWT всё равно живёт по часам и умирает вместе с `JWT_SECRET`, поэтому для интеграций есть
  долгоживущие ключи (`/api/tokens`): только SHA-256 в базе, `prefix` как ключ поиска, отзыв
  строкой, а не удалением, и открытый текст один раз в `201`.
- **Список разрешённых адресов.** Подпись отвечает «кто», адрес — «откуда»; проверка идёт после
  подписи и до `INSERT`, так что отклонённая доставка не оставляет следа в логе. Сравнение
  побайтовое, поэтому IPv4-mapped формы не обходят список. Ответ `403` называет адрес
  отправителя и число правил, но не сами диапазоны: сообщение читает тот, кому только что
  отказали.
- **Роли.** `users.role` — отдельное ограничение: оно живёт на человеке, а не на предъявленном
  токене, поэтому не попадает в JWT и понижение действует со следующего запроса (иначе уволенный
  сотрудник сохранял бы доступ до истечения 12-часового токена). Проверяются оба ограничения:
  `viewer` получает `403` «Роль «наблюдатель»…» на любой изменяющий метод, даже с полным токеном,
  а `scope: read` отказывает `editor`. Управление аккаунтами вынесено в `Auth::requireAdmin`:
  редактор, который мог бы выдать себе `admin`, сделал бы роли декоративными. Демо-аккаунт и
  все существующие записи при миграции `013` получают `admin` — обновление не должно запирать
  оператора вне страницы, где роли выдаются. Себя понизить, себя удалить и убрать последнего
  администратора нельзя (`422`).
- **Пароли.** Проверяется только длина: 8–72 **байта** (верхняя граница — предел bcrypt, который
  молча обрезает всё длиннее). Правила «одна цифра, один спецсимвол» не добавлены намеренно: они
  предсказуемо приводят к `Password1!` и не увеличивают энтропию. Смена своего пароля
  (`POST /api/auth/password`) требует `current_password`, иначе украденный токен превращается в
  постоянный захват аккаунта; администратор может сбросить чужой пароль из `/api/users/{id}`.
  Ни хеш, ни значение пароля никогда не возвращаются и не попадают в журнал — только факт
  изменения.
- **Журнал аудита.** `GET /api/audit` читается любой ролью (редактор, не видящий, почему правило
  изменилось, просто гадает), но записывать в него нельзя ничем: строки добавляют сами
  изменяющие обработчики, и `Audit::record` работает best-effort — сбой `INSERT` уходит в
  `error_log`, потому что изменение уже применено и `500` соврал бы о том, что «ничего не
  произошло». Записи денормализованы и переживают удаление объекта. Секреты подписи вырезаются
  до построения дифа, так что журнал не становится второй копией `rooms.secret` для всех
  читателей.
- **История версий.** Снимок хранит секрет подписи, иначе откат подписанной пересылки начал бы
  отправлять её без подписи — то есть «восстановление» сломало бы интеграцию. Поэтому чтение
  версии проходит через тот же `redactActions()`, что и чтение правила: `signed: true` вместо
  значения.
- **Подпись исходящих.** `forward` может нести `secret`: тело подписывается так же, как
  входящее (`X-Hookdock-Signature`), и получатель проверяет его тем же кодом. Секрет хранится в
  самом действии и поэтому, как и `rooms.secret`, никогда не возвращается API — вместо него
  `signed: true`. Из-за этого пустой `secret` при редактировании означает «оставить прежний»
  (иначе любая правка молча снимала бы подпись), а снятие — явный `clear_signature: true`.
  Прежний секрет переносится только при совпадении индекса **и** URL, иначе перестановка
  forward-ов в редакторе перенесла бы секрет одной цели на другую. Флаг `sign_timestamp` (по
  умолчанию `false`) добавляет к исходящим `X-Hookdock-Timestamp` и подпись по `"<ts>.<тело>"`;
  включать его для всех было бы нельзя — получатель, проверяющий HMAC только тела, ответил бы
  отказом. У действия может быть свой `timeout` (1–60 с, иначе `422`); без него используется
  `FORWARD_TIMEOUT`, а значение клампится в `HttpClient`, чтобы действие не держало слот очереди
  сколько попросит.
- **Защита от SSRF в `forward`.** Роутер работает внутри приватной сети, где незащищённая пересылка
  — это доступ к `api:9000`, к базе и к метаданным облака. Адреса сравниваются **побайтово**
  (`inet_pton`), а не строкой: `::1`, `0:0:0:0:0:0:0:1`, `::ffff:7f00:1`, `::ffff:127.0.0.1` и
  `::ffff:a9fe:a9fe` — это один и тот же адрес в разных записях, и строковое сравнение пропускает
  все, кроме первой. Отклоняются `0.0.0.0/8`, `127/8`, `169.254/16` (метаданные), multicast и
  broadcast, `::`, `::1`, `fe80::/10`, `ff00::/8` и любые IPv6-формы, внутри которых лежит
  запрещённый IPv4. Запуск сразу получает `failed`, без повторов. Имя хоста резолвится через
  `gethostbynamel` (единственный, кто видит `/etc/hosts` — там живут имена сервисов Docker и
  `ip6-localhost`) **и** `dns_get_record` A+AAAA; неразрешимое имя отклоняется (fail-closed), потому
  что при соединении оно резолвится заново. Приватные диапазоны (RFC1918 и `fd00::/8`) разрешены:
  пересылка на `http://web/...` — обычный сценарий. `FORWARD_ALLOW_INTERNAL=1` возвращает прежнее
  поведение, `FORWARD_BLOCKED_HOSTS` добавляет запрещённые хосты.
- **Соединение идёт на проверенный адрес.** `Support\HttpClient` работает через curl и пиннит хост
  к тем адресам, которые одобрила проверка (`CURLOPT_RESOLVE`) — иначе DNS-rebinding-имя может
  ответить «публичный адрес» при проверке и `127.0.0.1` при соединении. Редиректы не выполняются
  (они увели бы с проверенного адреса), протоколы ограничены `http,https`.
- **Лимиты запросов.** Неудачные входы считаются по аккаунту (10 в минуту, `LOGIN_MAX_ATTEMPTS`) и
  отдельно, мягче, по адресу (50 в минуту, `LOGIN_IP_MAX_ATTEMPTS`) — строгий лимит по IP заблокировал
  бы весь офис за одним NAT раньше, чем замедлил атакующего. Приём ограничивается
  `INGEST_MAX_PER_WINDOW` (по умолчанию 0 — без лимита, чтобы обновление не начало терять реальный
  трафик). Счётчики лежат в таблице `rate_limits`; при сбое лимитер пропускает запросы, чтобы
  сломанная таблица не заперла оператора в собственном дашборде.
- **Реальный IP клиента.** nginx передаёт `X-Real-IP` из `$remote_addr` (перезаписывая клиентское
  значение), `X-Forwarded-For` игнорируется. Без этого все запросы выглядели бы пришедшими из
  контейнера nginx и делили бы один счётчик.
- **Retention.** `RETENTION_DAYS` и `RETENTION_RUN_DAYS` (оба `0` = хранить всё) чистят старые
  запросы и завершённые запуски батчами по 1000, раз в час, в воркере. Проверка запускается на
  каждом проходе цикла, а не только когда очередь пуста, поэтому постоянная нагрузка её не
  вытесняет. Запуски в очереди не удаляются никогда, и запрос с незавершённым запуском пропускается
  — иначе очистка каскадом унесла бы ещё не выполненную доставку.
- **Поиск** использует trigram-индексы (`pg_trgm`): по телу (`006`) и по `path`/`endpoint` (`007`).
  Каждая из трёх ветвей фильтра индексируема, поэтому `?q=` не превращается в полный перебор. Значение
  экранируется: `%`, `_` и `\` — метасимволы `LIKE`, и без экранирования запрос `50%` находил бы всё,
  где есть «50».

## Реальное время

SPA не опрашивает API по таймеру. Вместо этого браузер держит WebSocket до контейнера `ws`:

```
api / worker ──NOTIFY hookdock_events──► ws ──► браузер
```

- `ws` — отдельный контейнер на том же образе, что `api`, с командой
  `php /var/www/backend/bin/ws-server.php`: один процесс, `stream_select`, ручной RFC6455.
- События в БД публикуются через `SELECT pg_notify(...)` в `Services\Realtime`; сбой публикации
  логируется и не влияет на ответ 202 приёмнику. Статус запуска публикует `worker`
  (`request.updated` с `status`).
- Доступ: `POST /api/ws/ticket` под JWT выдаёт 60-секундный тикет (`scope: ws`), с ним браузер
  открывает `/api/ws?ticket=…`. Тикет не пишется в access-log nginx.
- События: `request.created`, `request.updated`, `request.deleted`, `workflow.changed`,
  `room.changed`. Они несут только идентификаторы (и `room_id`), поэтому фронтенд делает тихую
  перезагрузку данных с дебаунсом 300 мс — фильтры, пагинация и счётчики всегда консистентны, а
  события чужой комнаты игнорируются на клиенте.
- Клиент переподключается с экспоненциальной задержкой (1→30 с) и после переподключения просит
  вкладки перечитать данные. Подписка всегда включена; в шапке «Входящих» рядом с кнопкой
  «Обновить» показывается только индикатор состояния канала (`в сети` / `переподключение…` /
  `нет соединения`).

## Интерфейс и темы

- Интерфейс полностью на русском; даты и числа форматируются под `ru-RU`.
- **Комнаты в боковой панели:** загружаются последние 20 со счётчиком запросов; остальные —
  через поиск по названию или slug (ввод с задержкой 300 мс, «лупа» и Enter ищут сразу). Под
  списком видно, сколько комнат всего. Кнопка «+ Комната», переименование и удаление по наведению.
  Выбранная комната определяет и лог, и сценарии; на мобильных список раскрывается кнопкой
  «Комнаты». Последняя открытая комната запоминается в `localStorage` (`wr_room`) и остаётся в
  списке, даже если она старше загруженной страницы; глубокие ссылки на удалённую комнату уводят в
  первую доступную.
- **Светлая тема включена по умолчанию.** Переключатель (солнце/луна) есть на странице входа и в
  боковой панели; выбор сохраняется в `localStorage` (`wr_theme`) и применяется до первой отрисовки.
- **Демо-кнопка на входе** показывается только при `DEMO_LOGIN=1`; креды приходят из
  `GET /api/auth/config`, поэтому в собранном JS их нет. Там же выводятся предупреждения
  конфигурации (например, дефолтный `JWT_SECRET`).
- Тема реализована CSS-переменными в `frontend/src/assets/main.css` и классом `.dark` на `<html>`
  (`@custom-variant dark` в Tailwind v4).
- Нативные контролы не используются напрямую: чекбоксы, селекты, поля, переключатели и textarea
  обёрнуты в компоненты `frontend/src/components/ui/*` — они держат единые размеры, фокус,
  disabled-состояния и цвета обеих тем. Для новых форм подключайте их, а не «сырые» `<input>`
  и `<select>`.
- `AppSelect` — полностью собственный выпадающий список: панель рисует компонент (через `Teleport`
  в `body`), а не браузер. Поддерживаются клавиатура (стрелки, Home/End, Enter, Esc, поиск по
  первой букве), закрытие по клику вне, переворот вверх у нижнего края экрана и пересчёт позиции
  при скролле — поэтому список не обрезается модалками и `overflow: hidden`.
- Автозаполнение браузера, стрелка селекта, кнопка очистки поиска, цвета выпадающих списков и
  скроллбары также приведены к стилю сайта.
- **Страница «Доставка»** — общая для установки: список адресов, которые сейчас пропускает
  предохранитель, с временем до следующей пробы и кнопкой сброса (после починки цели), экспорт
  правил текущей комнаты в файл и импорт такого файла. Адрес не принадлежит комнате, поэтому и
  таблица не сужается до одной.
- **Страница «Аудит»** — лента изменений установки: время, автор с ролью, действие, комната и
  объект, плюс раскрывающийся диф `{поле: [было, стало]}`. Фильтры — комната, действие, автор и
  поиск по тексту; записи приходят в реальном времени событием `audit.recorded`. Читается любой
  ролью: редактор, не видящий, почему правило изменилось, остаётся гадать.
- **Страница «Пользователи»** — аккаунты, роли и сброс пароля; пункт меню виден только
  администратору, потому что сама страница ответила бы `403` остальным. Свою роль снять и свой
  аккаунт удалить нельзя — кнопки для этого нет, а API отказал бы и напрямую.
- **История версий сценария** открывается из списка правил: сохранённые конфигурации с автором,
  причиной (`created`/`update`/`toggle`/`import`/`rollback`) и временем, предпросмотр снимка и
  откат одной кнопкой. Откат показан как новое сохранение, а не как удаление истории, поэтому
  ошибку можно отменить тем же списком.
- **Один индикатор загрузки на экран.** Список ждёт данных из нескольких независимых источников
  (первичная загрузка, перезагрузка по фильтру с минимальной длительностью, кнопка «Обновить»), и они
  пересекаются. Поэтому оверлей и встроенный спиннер выводятся из одного условия и взаимоисключающие:
  оверлей — когда есть строки, которые можно затемнить, спиннер в таблице — когда показывать нечего.
  Спиннер в фильтре метода убран: он дублировал тот же процесс. При переходе между комнатами строки и
  счётчики предыдущей комнаты очищаются до ответа, повторная загрузка из-за сброса фильтров
  подавляется, а устаревший ответ не перерисовывает список новой комнаты.

## Разработка

PHP и база рассчитаны на запуск в контейнерах. Глобального middleware авторизации нет: каждый
маршрут API сам вызывает `Auth::requireUser($request)`, изменяющие — `requireUser($request, true)`,
а управление аккаунтами — ещё и `requireAdmin($request)`; маршруты вебхуков намеренно публичны.
Роль читается из таблицы `users` на каждом запросе, поэтому она не попадает в JWT: иначе
понижение ждало бы истечения токена 12 часов. HTML формирует только nginx; `/` отдаёт
`index.html`, поэтому history-mode роутер работает при перезагрузке.

Горячая перезагрузка фронтенда:

```bash
# стек уже запущен на :8080
cd frontend
npm.cmd install
npm.cmd run dev        # http://localhost:5173, прокси /api и /hook на :8080
```

Проверка production-сборки: `npm.cmd run build` (Tailwind v4 подключён через `@tailwindcss/vite`,
файла `tailwind.config.js` нет).

Миграции: добавьте `backend/migrations/00N_name.sql` — файл применится при следующем старте `api`
и запишется в `schema_migrations`. Уже применённые файлы не редактируйте.

Полезные команды:

```bash
docker compose logs -f api
docker compose logs -f worker       # маршрутизация: запуски, повторы, ошибки действий
docker compose logs -f ws           # realtime daemon: подключения и доставка событий
docker compose restart ws           # клиенты переподключатся сами
docker compose exec api php migrate.php
docker compose exec db psql -U webhooks -d webhooks
docker compose run --rm worker php /var/www/backend/bin/worker.php --once   # разобрать очередь и выйти
docker compose down -v          # полный сброс, удаляет том pgdata
```

## Проверка

`scripts/smoke.ps1` проверяет вход, отказ без токена, CRUD комнат (включая отказ на дубликат и
невалидный slug, сохранение slug при переименовании), приём вебхука в комнату, изоляцию комнат
(запрос не виден в чужой, сценарий чужой комнаты не срабатывает), совпадение и пропуск условий,
сохранение не-JSON тела, forward-действие, разрешение адресов `/hook/{room}/{endpoint}`,
`/hook/{room}`, `/hook/{endpoint}` и 404 на неизвестную комнату, пагинацию, статистику, а также что
JSONB-поля приходят массивами/объектами и что сценарий можно создать на паузе. Отдельные секции
проверяют глубокие пути (`/hook/{room}/deep/a/b/c` сохраняется целиком, неизвестная комната —
404), тела `multipart/form-data` (сохраняются, а не теряются в разборе форм PHP), CORS-preflight
(`204` и `*`), а настоящий `OPTIONS`-вебхук всё равно принимается. Отдельная секция про
безопасность: тикет WebSocket не проходит как токен API, повторные неверные пароли получают `429`,
а каждая запись loopback отклоняется без повторов — `169.254.169.254`, `[::1]`, развёрнутая форма
`[0:0:0:0:0:0:0:1]`, IPv4-mapped `[::ffff:7f00:1]` и `[::ffff:127.0.0.1]`, а также `ip6-localhost`
(имя из `/etc/hosts`, которого нет в DNS). Отдельный кейс проверяет, что `%` и `_` в поиске не
работают как подстановочные знаки. Маршрутизация асинхронная,
поэтому все проверки запусков идут через `Wait-ForRuns`: они ждут, пока `worker` доведёт запуск до
финального статуса. Проверяются также журнал шагов (тип действия и код ответа), повтор при
недоступном адресе (`failed`, `attempts ≥ 2`), отсутствие повтора уже успешного действия (шаг `log`
в журнале один, хотя запуск повторялся) и поле `queued` в ответе приёмника. Поиск по телу
проверяется вместе с пустой выдачей.

Отдельные блоки покрывают то, что появилось позже: дерево условий (`type = payment AND (name = Ada
OR name = Bob)` и четыре отказа валидации — глубина, число листьев, неизвестный оператор, пустая
группа), `delay` (запуск возобновляется один раз и не сжигает попытку), `priority` +
`stop_processing` (остальные запуски запроса становятся `skipped`, а сообщение называет
остановивший сценарий), `duplicate` (копия создаётся на паузе), `preview` (черновик, все правила
комнаты, отказ `UrlGuard` — и что запуск при этом не появляется), подпись исходящих
(`signed`/`clear_signature`, «пустой `secret` сохраняет прежний»), скачивание тела, `/api/runs` и
токены только для чтения (`403` на каждом изменяющем методе). Блок «дедупликация, timestamp и
таймаут действия» проверяет: первый ключ доставки ставит правило в очередь, повтор сохраняется в лог
с `duplicate_of`, но не маршрутизируется и всё равно получает `202`; доставка без настроенного
заголовка обрабатывается как обычная; комната без настройки не дедуплицирует; timestamp-подпись
принимается, body-only рядом с заголовком времени — нет, старое время отклоняется; `timeout`
сохраняется и отражается в dry-run, `0` и `61` отклоняются; переименование комнаты сохраняет
`dedup_header`, а пустая строка его выключает. Блок волны 2 проверяет предохранитель пересылки
(серия терминальных сбоев открывает адрес, отказ записывается шагом `skipped` и откладывает запуск
без сжигания попытки, `deferrals` растёт, dry run описывает состояние и **не** забирает пробу,
сброс удаляет строку и адрес снова вызывается), экспорт и импорт правил (файл без секретов,
`signed: true` вместо значения, импорт в ту же комнату даёт суффиксы, `secrets_not_imported`,
`room_id` только из URL, `422` на документ без правил, `404` на чужую комнату) и оптимистическую
блокировку (`409` со `current`-версией на устаревший черновик, отказ не трогает сохранённые
действия, переименование не поднимает версию, реальное изменение — поднимает). Блок волны 3
проверяет роли и доступы: `admin` создаёт `viewer` и `editor`, дубликат email/короткий пароль/
неизвестная роль — `422`, `viewer` читает лог, аудит и историю версий, но получает `403` на каждый
изменяющий метод, `editor` пишет, но не управляет аккаунтами и не может создать `admin`, смена
своего пароля требует текущий и не действует без него, понижение роли действует на уже выданном
токене, себя понизить и удалить нельзя. Журнал аудита: создание комнаты записывается с автором,
ролью и названием объекта, скопированный slug остаётся прежним после переименования, диф роли
показывает `editor → viewer`, фильтры по комнате/действию/автору/тексту работают, неизвестное
действие — `422`, а секрет подписи в дифе не появляется (`signed: true` вместо значения). История
версий: первая версия `created`, переименование добавляет версию, но не меняет
`actions_version`, реальное изменение действий — меняет, список отсортирован новыми сверху,
чтение версии не отдаёт секрет, откат добавляет `rollback`-версию (старые остаются), откат
попадает в аудит, отсутствующая версия и история отсутствующего правила — `404`.
Блок волны 4 проверяет массовые операции и повтор с правкой: запрос ниже порога правилом не
совпадает, а его копия с исправленным телом — совпадает; исходная строка при этом не меняется ни в
`body`, ни в `raw_body`, не помечается `replayed_from` и сохраняет адрес отправителя у копии;
копия не получает `dedup_key` (иначе комната посчитала бы её повтором самой себя и не
маршрутизировала); массовый повтор возвращает `count`/`queued`, отсутствующий id попадает в
`missing`, а не роняет пачку, неизвестное действие/пустой список/`ids` строкой — `422`; запрос с
ещё выполняющимся запуском не удаляется и попадает в `skipped`, после чего его запуск спокойно
завершается; одна запись аудита на пачку (`request.bulk_deleted`) с числом строк; токен только для
чтения и `viewer` получают `403` на оба вызова.
Блок волны 5 проверяет наблюдаемость: поиск находит доставку по значению заголовка (и по имени
заголовка без учёта регистра, а промах даёт пустую страницу), аналитика отдаёт окно, раскладку по
методам/исходам/типам действий и таймлайн из `hours + 1` бакетов, сумма `requests` в котором равна
общему числу запросов; `hours=0` откатывается к суткам, `1000` обрезается до недели, неизвестная
комната — `404`, без токена — `401`, а токен только для чтения числа читает. Метрики публичны,
отдаются как `text/plain`, сообщают `hookdock_api_up`/`hookdock_database_up`, помечают запуски
статусом, считают открытые предохранители **без** адреса, объявляют `# TYPE` ровно один раз и не
содержат ни полезной нагрузки, ни slug'а комнаты.
Блок волны 6 проверяет управление доступом. Список адресов хранится канонически и без дубликатов
(` 198.51.100.7 ` → `198.51.100.7/32`), доставка из разрешённого диапазона принимается, а с чужого
адреса получает `403` и **не появляется в логе** (сравнивается `meta.total` до и после); `out-of-range`
префикс и непарсящаяся запись — `422`, переименование комнаты сохраняет список, а явный `[]` его
выключает, изменение попадает в аудит. Долгоживущие токены: `admin` видит список без значений и
хешей, новый ключ по умолчанию `read` и начинается с `hd_` (`prefix` — его начало), `GET
/api/auth/me` сообщает `scope: read` и `can_write: false`, чтение лога разрешено, а запись, список
токенов и выпуск нового ключа — `403`; `editor` и `viewer` список не видят; полный `api`-ключ
пишет; неизвестный scope/пустое имя/прошедшая дата — `422`, голая дата означает конец дня
(`23:59:59`), неизвестный ключ — `401`; отзыв действует на следующем запросе, повтор даёт
`already: true`, отсутствующий id — `404`, а отозванная строка остаётся в списке с `last_used_at`.
Секция реального
времени проверяет, что тикет выдаётся только с JWT, WebSocket поднимается через nginx, приходит
`hello`, а приём вебхука доставляет `request.created` с его `id` и `room_id` (секция скипается,
если в PowerShell недоступен `System.Net.WebSockets.ClientWebSocket`). Скрипт убирает за собой
созданные данные.

`scripts/smoke.ps1` — единственный тест в проекте, поэтому он же и гейт в CI
(`.github/workflows/ci.yml`): отдельная задача собирает SPA (`npm ci` + `npm run build`), вторая
поднимает стек через `docker compose up -d --build`, ждёт `healthy` у `api` (это значит, что
миграции применились) и запускает смоук через `pwsh` — GitHub Actions работает на Linux, где есть
PowerShell 7.

## Примечания

- При обновлении со старой версии миграция `002_rooms.sql` очищает прежние запросы, запуски и
  сценарии (`TRUNCATE … RESTART IDENTITY`) и заводит комнату «Общая» — данные не переносятся
  автоматически. Уже применённая миграция повторно не выполняется.
- Пароль администратора хранится как bcrypt-хеш; смените его после первого входа в реальном
  окружении.
- Миграция `013` выдаёт `admin` всем существующим аккаунтам: обновление не должно оставлять
  установку без доступа к странице, где роли выдаются. Дальше роли раздаются через
  `PUT /api/users/{id}`, а себе роль `admin` снять нельзя — для этого нужен второй администратор.
- Перед публикацией наружу задайте надёжный `JWT_SECRET` и смените `DB_PASSWORD`, а также
  выключите `DEMO_LOGIN`. Страница входа покажет предупреждение, если секрет остался дефолтным.
- nginx и PHP ограничивают тело вебхука 16 МБ.
- Forward-действия выполняются из контейнера `worker`: во внутренних URL используйте DNS сервисов
  (`http://web/...`), а не `localhost:8080`.
- Маршрутизация асинхронная, поэтому ответ `202` означает «сохранено и поставлено в очередь», а не
  «действия выполнены». Итог смотрите в карточке запроса (статус запуска и шаги) или в
  `docker compose logs -f worker`.
- Очередь — это таблица `workflow_runs` (статусы `pending`/`running`), её разбирает `worker` через
  `FOR UPDATE SKIP LOCKED`. Несколько реплик `worker` безопасны, но строгий порядок запусков одного
  запроса между ними не гарантируется.
- `worker` запускается с `RUN_MIGRATIONS=0` и ждёт схему от `api`, поэтому холодный старт не
  приводит к циклу перезапусков. Зависшие `running`-запуски возвращает в очередь
  `recoverStale()` (`ROUTING_STALE_MINUTES`).
- Контейнер `ws` — единственный экземпляр: события между клиентами распределяет он один. Для
  нескольких реплик `LISTEN/NOTIFY` недостаточно (каждая получит своё уведомление) — понадобится
  общий брокер, например Redis pub/sub.
- Лимиты запросов используют фиксированное окно: на границе двух окон возможен всплеск до двух
  лимитов подряд. Для защиты формы входа этого достаточно; если понадобится строгий предел,
  следующий шаг — скользящее окно (`rate_limits` уже хранит метку окна).
- `fd00::/8` (IPv6 ULA) разрешён намеренно, как аналог RFC1918: внутренняя пересылка по IPv6 —
  такой же штатный сценарий, как `http://web/...`. Хост из этого диапазона можно закрыть точечно
  через `FORWARD_BLOCKED_HOSTS`.
